# Phase 18: Agent Swarm & Provider Gateway Security Architecture

## 1. Core Security Principle: Zero Trust Agent Federation

In Hey Jev Phase 18, remote agent workers, external model providers, and web endpoints are treated as untrusted boundaries:
$$\text{External Agent Output} = \mathbf{DATA},\quad \text{NOT EXECUTABLE POLICY}$$

No external agent response, model completion, or remote message has the authority to:
1. Elevate its own permissions or grant new scopes to other agents.
2. Override Jev's core system prompt or safety rules.
3. Automatically execute unverified shell commands or write arbitrary local files without verification.
4. Access or transmit stored user credentials or sensitive memory tiers.

---

## 2. Remote Agent Trust Hierarchy

Every worker and provider operates under an explicit, enforceable trust tier:

| Trust Tier | Definition | Allowed Capabilities | Restricted Capabilities |
| :--- | :--- | :--- | :--- |
| `LOCAL_TRUSTED` | In-process Python components, local Antigravity CLI in verified local path. | File I/O within project boundaries, shell execution with user consent, access to `NORMAL` memories. | System directory tampering, unauthenticated network exfiltration. |
| `VERIFIED_REMOTE` | Known cloud endpoints with user-configured API keys (OpenAI, Anthropic, known A2A endpoints). | Semantic inference, code generation, structured analysis. | Direct access to OS files, raw secrets, persistent memory `SENSITIVE` tier, direct shell execution. |
| `COMMUNITY_REMOTE` | External A2A federated agents, third-party search endpoints. | Read-only analysis, broad search queries, external opinion emission. | Zero file access, zero command execution, stripped of all personal context. |
| `UNTRUSTED` | Web pages scraped during browser fallback, unverified third-party models. | Pure text extraction, raw text candidate proposals. | Strictly quarantined; output subjected to adversarial sanitization before use. |

---

## 3. Artifact Trust Specification

When a worker produces an artifact (file, patch, script, or analysis document), the artifact must carry cryptographically verifiable trust metadata:

```json
{
  "artifact_id": "art_7f8a9b1c",
  "producer_agent": "worker_research_1",
  "provider": "openai_compatible",
  "trust_level": "VERIFIED_REMOTE",
  "source_task_id": "task_44a10f",
  "created_at": 1791352000.0,
  "checksum": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "verified_by": "verifier_agent",
  "is_executable": false
}
```

### Invariants:
- **No Automatic Execution**: Artifacts marked with `is_executable: true` generated by remote or untrusted agents cannot be executed without explicit review and deterministic verification.
- **Checksum Verification**: The hash of any artifact received from a remote worker must match before ingestion into memory or project storage.

## 4. Secret Sanitization & Request Redaction

Before transmitting any task context, goal, or history to an external model or remote A2A worker, the payload passes through the **Secret Redaction Pipeline**:

1. **Pattern Scrubbing**:
   - Matches known API key formats (`sk-proj-*`, `ghp_*`, `AIza*`, bearer tokens, private keys).
   - Replaces matches with `[REDACTED_SECRET]`.
2. **Sensitivity Gating**:
   - Phase 16 Memory records with sensitivity tier `SENSITIVE` or `PRIVATE` are strictly excluded from external requests.
   - Only `PUBLIC` or filtered `NORMAL` project memories are transmitted to `VERIFIED_REMOTE` workers.
3. **Context Minimization (Need-to-Know)**:
   - Workers receive only the specific slice of context required for their assigned role (e.g., Coder receives diff + failing test; Researcher receives topic + search terms; Reviewer receives diff + criteria).

---

## 5. Defense Against Prompt Injection & Self-Granting Escalation

1. **Instruction Boundary**:
   - System prompts, user goals, tool descriptions, and external model responses are isolated into discrete JSON fields.
   - When external completions are fed back into synthesis or review loops, they are enclosed within explicit data tags (e.g. `<external_worker_output>` ... `</external_worker_output>`).
2. **No Self-Granting Permissions**:
   - A worker may request a permission (e.g., `requires_permissions: ["NETWORK_ACCESS"]`), but the `SwarmPlanner` and Jev `ResourceGovernor` alone determine whether the permission is granted.
   - External workers cannot modify their own permissions or spawn sub-workers.
3. **Spawn Depth Bounding**:
   - `max_spawn_depth = 1`: Workers cannot spawn new child swarms or delegate recursively. All workers report directly to the root swarm orchestrator.

---

## 6. Financial & Budget Safety

1. **Zero-Budget Enforcement**:
   - When `max_cost = 0.0` or `COST_MODE = FREE_FIRST`, the `ProviderGateway` strictly blocks calls to paid API endpoints, routing only to local tools, local models, or free providers.
2. **Multi-Constraint Budget Limits**:
   - Swarms enforce four distinct budget thresholds:
     - `max_cost`: Dollar cap (e.g., \$0.50).
     - `max_requests`: Call count cap (e.g., 10 API requests).
     - `max_tokens`: Total token limit (e.g., 20,000 tokens).
     - `max_wall_time`: Timeout cap (e.g., 120 seconds).
   - Once any threshold is exceeded, the worker transitions to `BLOCKED` or the swarm transitions to `WAITING_FOR_APPROVAL`.

---

## 7. Browser Transport Fallback Safety

When invoking browser transport as an emergency fallback:
- **Dedicated Isolated Profiles**: Browser automation runs in clean, ephemeral session profiles.
- **Zero Cookie / Credential Scraping**: Jev never extracts stored browser passwords or session cookies to pass to external agents.
- **No CAPTCHA / Auth Bypassing**: Automation immediately yields with `AUTH_REQUIRED` if a CAPTCHA or two-factor prompt is encountered.
